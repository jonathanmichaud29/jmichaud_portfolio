# Environment Variables and Secrets

This is part 7 of the series. At this point the repository structure, base images, Compose topology, Dev Container configuration, volume strategy, and UID/GID mapping are all settled. Before anyone writes a service, we need to answer one deceptively broad question: **where do credentials live, who generates them, and what prevents a bad value from reaching a running container?**

---

## The problem with "just use .env"

Most projects collapse everything into one `.env` file and one `.env.example`, gitignore the former, and call it done. This works until it doesn't — a developer commits `.env` because the gitignore had a typo, someone copies a staging credential into their local file, or a new variable gets added to the app but never documented in the example. The failure is always silent.

The solution is not more files. It's a deliberate taxonomy, one enforced file format, and tooling that generates what can be generated and blocks what isn't ready.

---

## Taxonomy of values

Four categories, each with different security posture and different treatment:

| Category                | Examples                               | Committed?                 | Generated?                  |
| ----------------------- | -------------------------------------- | -------------------------- | --------------------------- |
| Infrastructure          | `UID`, `GID`, `COMPOSE_PROJECT_NAME`   | As `REPLACE_ME` in example | Yes — `make init`           |
| App config (non-secret) | `APP_ENV`, `LOG_LEVEL`, `API_BASE_URL` | Safe defaults directly     | No — defaults are fine      |
| Generated secrets       | `DB_PASSWORD`, `APP_KEY`               | As `REPLACE_ME` in example | Yes — `make init`           |
| Third-party credentials | `STRIPE_SECRET_KEY`, external API keys | As `REPLACE_ME` in example | No — manual, with docs link |

The distinction between "generated secrets" and "third-party credentials" is the key design decision. Anything the project controls (database password, app signing key, session secret) can be randomly generated at init time — there is no reason a developer should ever type these. Anything that requires an external account or a real API relationship cannot be generated and must be documented clearly.

---

## File structure

Two files. Not one, not three.

```
.env.example    # committed to the repository
.env            # gitignored, generated by make init
```

`.env.example` is the contract. Every variable the application or Compose topology needs must appear here. It is the single source of truth for what exists — if a variable is not in `.env.example`, it does not exist as far as onboarding is concerned.

`.env` is never committed. If it is ever found in a pull request, that is a process failure, not a developer failure — the `.gitignore` entry is the first line of defence.

### Why not split infrastructure vars into a separate file?

The alternative — `.env.infra` for `UID`/`GID` and Compose concerns, `.env` for application secrets — was considered and rejected. It requires `env_file: [.env.infra, .env]` on every Compose service, or merging files in the Makefile before Compose sees them. For a small team this complexity produces no meaningful benefit. Logical separation via comment sections in one file is sufficient.

### Why not `docker-compose.override.yml` for credentials?

`override.yml` was established in Part 3 as the escape hatch for host-specific concerns: port remapping, personal tooling mounts. Credentials must not live there. The `override.yml` already has a committed `.example` file — mixing secrets into that flow creates two gitignored files that can contain credentials, doubling the surface area for accidents. Secrets live exclusively in `.env`.

---

## The sentinel pattern

Every value that requires action — whether generated or manual — uses `REPLACE_ME` as its placeholder in `.env.example`. One pattern, `grep`-able, unambiguous.

```bash
# === Infrastructure (generated by make init) ===
UID=REPLACE_ME
GID=REPLACE_ME
COMPOSE_PROJECT_NAME=my-project

# === Application config (safe defaults — no action needed) ===
APP_ENV=local
LOG_LEVEL=debug
API_BASE_URL=http://api:8080

# === Generated secrets (make init replaces these automatically) ===
DB_PASSWORD=REPLACE_ME
APP_KEY=REPLACE_ME

# === Third-party credentials (manual — see docs/credentials.md) ===
STRIPE_SECRET_KEY=REPLACE_ME
```

No empty strings, no commented-out lines. Empty strings are ambiguous — some drivers treat an empty password as valid and silently connect. A sentinel is explicit: this value was never set, and anything consuming it is misconfigured.

## The Makefile

Three targets with distinct responsibilities:

```
make init       → bootstrap only — copies, generates, informs
make build      → calls _preflight, then docker compose build
make up         → calls _preflight, then docker compose up
```

`_check-env` and `_preflight` are internal targets. The underscore prefix is a team convention signalling "not a direct entry point" — Make does not enforce this, but it communicates intent. Both must still appear in `.PHONY` because Make needs to know they are not files.

### `_check-env` — inform, never block

Called at the end of `make init`. Its only job is to tell the developer what still needs manual action. It never exits with a non-zero code.

```makefile
_check-env:
	@MISSING=$$(grep -E "^[^#].*=REPLACE_ME" .env | cut -d= -f1); \
	if [ -n "$$MISSING" ]; then \
		echo ""; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		echo "⚠️  Action required — manual credentials needed"; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		echo ""; \
		echo "The following variables still require manual setup:"; \
		echo ""; \
		for var in $$MISSING; do echo "  • $$var"; done; \
		echo ""; \
		echo "📖 docs/credentials.md"; \
		echo "   https://github.com/your-org/your-repo/blob/main/docs/credentials.md"; \
		echo ""; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		echo ""; \
	else \
		echo "✅ .env is fully configured — run: make up"; \
	fi
```

### `_preflight` — enforce, hard block

Called before every `make build` and `make up`. Checks that `.env` exists and contains no remaining `REPLACE_ME` values. Exits non-zero if either condition fails, preventing Docker from ever seeing an unconfigured credential.

```makefile
_preflight:
	@test -f .env || { \
		echo "🚫 .env not found — run: make init"; \
		exit 1; \
	}
	@MISSING=$$(grep -E "^[^#].*=REPLACE_ME" .env | cut -d= -f1); \
	if [ -n "$$MISSING" ]; then \
		echo ""; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		echo "🚫 Build blocked — credentials not configured"; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		echo ""; \
		echo "The following variables in .env still contain REPLACE_ME:"; \
		echo ""; \
		for var in $$MISSING; do echo "  • $$var"; done; \
		echo ""; \
		echo "📖 docs/credentials.md"; \
		echo "   https://github.com/your-org/your-repo/blob/main/docs/credentials.md"; \
		echo ""; \
		echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"; \
		exit 1; \
	fi
```

### `init` — the full bootstrap sequence

```makefile
init:
	@test -f .env && { echo "⚠️  .env already exists. Delete it manually to reinitialize."; exit 1; } || true
	@cp .env.example .env
	@# Infrastructure
	@perl -i -pe "s/^UID=REPLACE_ME/UID=$(shell id -u)/" .env
	@perl -i -pe "s/^GID=REPLACE_ME/GID=$(shell id -g)/" .env
	@# Generated secrets
	@perl -i -pe "s/^DB_PASSWORD=REPLACE_ME/DB_PASSWORD=$(shell openssl rand -base64 16 | tr -dc 'a-zA-Z0-9' | head -c 20)/" .env
	@perl -i -pe "s/^APP_KEY=REPLACE_ME/APP_KEY=$(shell openssl rand -hex 32)/" .env
	@$(MAKE) _check-env
```

`make init` is intentionally a one-time operation. If `.env` already exists, it exits immediately with a message. The developer deletes `.env` manually if they want a clean reinitialize — this friction is deliberate. An accidental `make init` on a configured environment should not silently regenerate passwords and break running containers.

### Full `.PHONY` declaration

```makefile
.PHONY: init build up _preflight _check-env
```

Every non-file target appears here regardless of whether it is "public" or "internal." `.PHONY` is a Make correctness mechanism, not an access control mechanism.

---

## Why `perl -i` over `sed -i`

`sed -i` is not portable. On macOS it requires `sed -i ''`; on GNU/Linux it requires `sed -i`. Since the Makefile runs on the host — not inside a container — and the team is on mixed macOS/Linux/WSL2, a `sed -i` call will silently produce wrong results or fail on at least one platform.

`perl -i` is consistent across all three environments without branching. It is available by default on macOS, all Linux distributions, and WSL2. No installation required.

---

## Secret generation

Two strategies, each appropriate to its use case:

```makefile
# High-entropy hex — app signing keys, session secrets
APP_KEY=$(shell openssl rand -hex 32)

# Alphanumeric password — database passwords, broker credentials
DB_PASSWORD=$(shell openssl rand -base64 16 | tr -dc 'a-zA-Z0-9' | head -c 20)
```

`openssl` is available on all target platforms without installation. The base64-then-filter approach for passwords strips characters that cause problems in shell interpolation or connection strings (`+`, `/`, `=`), producing a clean alphanumeric string without pulling in `pwgen` or any other dependency.

---

## Third-party credentials

Third-party API keys (`STRIPE_SECRET_KEY` and equivalents) cannot be generated. `make init` leaves these as `REPLACE_ME`, and `_check-env` prints them explicitly with a link to `docs/credentials.md`.

`_preflight` then hard-blocks `make build` and `make up` until they are filled in. A developer working on a service that does not need Stripe locally still sees the warning from `_check-env` at init time, but `_preflight` will block them at build time. This is intentional: every variable in `.env.example` is required by something in the stack, and the enforcement is global.

If selective enforcement becomes necessary (worker developer who never touches payment flows), the correct solution is to split `.env.example` sections with clearer documentation, not to weaken `_preflight`.

---

## CI

GitHub Actions does not use a `.env` file. Secrets are injected as repository secrets and passed as `env:` variables directly to workflow steps. The container receives them via `docker run -e VAR=${{ secrets.VAR }}`. No `.env` file is written to the runner filesystem.

`.env.example` remains the contract: the variable names declared there must match exactly what CI injects. If a new variable is added to `.env.example`, a corresponding secret must be added to the GitHub repository before the next CI run.

## Developer onboarding sequence

```
git clone <repo>
cd my-project
make init          # copies .env.example, generates secrets, warns on manual items
                   # → follow docs/credentials.md for third-party keys
# ... fill in remaining REPLACE_ME values in .env ...
make up            # _preflight validates, hard blocks if anything remains
```

Three commands from clone to running containers. The only variable step is the manual credential setup, and `_check-env` tells the developer exactly what needs doing and where to find the instructions.

---

## Decisions not made here

- **Secrets manager integration** — 1Password CLI (`op inject`), Vault, or AWS Secrets Manager are all viable futures. The `.env.example` format is compatible with `op inject` without changes. Adopt when team size makes manual credential rotation painful.
- **Docker Compose `:?` validation** — Compose supports `${VAR:?error message}` syntax to block service startup on missing variables. Acknowledged as a valid third enforcement layer but not adopted here to keep Compose files readable during the proof-of-concept phase.
- **`.env` per service vs single root `.env`** — One root `.env` consumed by all services via `env_file:` in each `compose.yml`. Per-service `.env` files were not evaluated; they would complicate `make init` and drift more easily.

---

## Artifacts produced

- `.env.example` — committed, structured with comment sections, `REPLACE_ME` sentinels throughout
- `.env` — gitignored, generated by `make init`, never committed
- `Makefile` — `init`, `build`, `up`, `_preflight`, `_check-env` targets
- `docs/credentials.md` — manual credential setup instructions, linked from all warning messages
